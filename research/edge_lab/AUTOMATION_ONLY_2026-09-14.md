# Automation Only — 2026-09-14

## 新硬规则

从本轮起，任何需要持续人工做任务、人工抢单、人工创作、人工找客户的项目，全部降级。

唯一保留的候选必须尽量满足：

1. 平台已经有买家/需求，不需要主动获客；
2. 数字商品或机器服务可以自动交付；
3. 交易、授权、结算由平台处理；
4. 人只负责首次构建、偶尔维护和异常处理；
5. 零本金或接近零本金；
6. 适合单人小容量，不依赖大规模扩张；
7. 不是利用支付、账号、风控等未授权漏洞。

## 当前最强母结构：生态迁移缺口

目标不是做“大软件”，而是在一个快速迁移的开发生态里，寻找非常窄的兼容性缺口。

以 DCloud / uni-app / uni-app x / HarmonyOS 为样本：

- 官方文档有细粒度的平台兼容表；
- HarmonyOS 原生 API 可以通过 UTS/ArkTS 插件封装；
- DCloud 插件市场提供付费销售、试用、授权和自动结算；
- 个人作者可以实名收款；
- 平台收取 15% 服务费，剩余收益按月结算；
- 用户自己在市场里搜索插件，不需要我们逐个找客户。

因此可以形成：

`官方兼容表 → 找 HarmonyOS 缺口 → 检查插件市场供给 → AI 生成/补齐插件 → 测试 → 上架 → 平台自动销售/授权/结算`

## 为什么这比众包任务更符合目标

众包任务的收入本质仍然与人工时间线性相关；插件市场则允许一次构建，多次自动销售。

最关键的是：

- 市场需求已经存在；
- 用户有明确搜索意图；
- 小插件客单价不需要很高；
- 单个细分需求对大公司不重要，但对个人可能够用；
- 大量插件只需要做很窄的一件事。

这更接近“地下城低级图”：单个功能很小，别人觉得不值得做，但对单人可以重复产生收益。

## 自动找缝机制

不靠主观猜插件，而是建立 Gap Scanner：

### 输入 A：官方兼容矩阵

抽取：

- API / 能力名
- Android 支持状态
- iOS 支持状态
- HarmonyOS 支持状态
- 是否支持 uni-app
- 是否支持 uni-app x
- 是否需要原生能力

### 输入 B：插件市场供给

抽取：

- 插件标题/关键词
- 是否支持 HarmonyOS
- 是否付费
- 购买量/下载量/收藏量（如果页面公开）
- 最近更新时间
- 竞争插件数量

### 机会评分

候选分数：

`GapScore = CommonNeed × PlatformGap × LowSupply × AutoDelivery × NoExternalCost × Maintainability`

其中：

- CommonNeed：Android/iOS 常见业务是否经常用到；
- PlatformGap：HarmonyOS 是否仍缺失或不完整；
- LowSupply：市场里成熟插件是否很少；
- AutoDelivery：是否能完全数字化交付；
- NoExternalCost：是否不依赖收费 API / 服务器；
- Maintainability：升级后维护成本是否可控。

## 第一轮人工核验结果

### 已饱和 / 暂不做

- NFC：已有多款 Android/iOS/HarmonyOS 三端插件；
- 文件选择器：已有多款全端插件；
- 微信登录/分享/支付：已有成熟三端插件；
- 扫码：已有全端插件；
- 后台定位/保活：已有多款；
- 防截屏/录屏：已有多款；
- ESC/POS 打印：2026 年已有新插件补齐 HarmonyOS。

这验证了 Gap Scanner 的必要性：很多看起来“鸿蒙新生态”的功能其实已经被填平，不能凭感觉进场。

### 值得继续盯的缺口：三端安全存储

目前检索到的安全存储插件主要覆盖 Android Keystore + iOS Keychain，HarmonyOS 明显没有被同一插件完整覆盖；而另一类插件只是提供加密算法，并不等于系统级安全存储。

潜在产品：

**Cross-Secure-Store**

统一 API：

- set(key, value)
- get(key)
- remove(key)
- has(key)
- clear()
- getCapabilities()

平台实现：

- Android：Keystore + 私有密文存储；
- iOS：Keychain；
- HarmonyOS：KeyStore / HUKS + Preferences / 应用沙箱；

价值不是“写几个函数”，而是把三端安全存储的差异、异常、迁移、示例和版本兼容打包成一个可直接购买的插件。

这只是第一个候选，不直接认定为财路。必须继续扫描更多能力并比较供给密度。

## 自动化程度

理想流水线：

1. 每天/每周爬取官方兼容表；
2. 对比上一次快照；
3. 发现 HarmonyOS 新缺口/新变化；
4. 搜索插件市场已有供给；
5. 自动生成候选列表和评分；
6. AI 为 Top 3 生成实现草案、测试矩阵、README、Demo；
7. 人只决定做/不做，并完成必要真机验证；
8. 上架后销售、授权、交付、结算自动运行。

## 淘汰标准

任何候选出现以下情况直接砍：

- 市场已有 3 个以上成熟三端插件；
- 依赖付费服务器或第三方 API 才能运行；
- 每卖一份都需要人工配置；
- 售后无法标准化；
- 需要持续人工操作才能产生收入；
- 只能靠主动拉客户成交；
- 涉及绕过平台授权、风控或支付机制。

## 当前判断

相比“夜间做众包”，`生态兼容缺口插件` 更符合自动化要求。

真正应该开发的不是一个固定插件，而是：

**一台持续发现生态迁移小缺口的机器。**

找到一个小缺口 → 做一个极窄插件 → 上架自动卖 → 继续扫描下一个缺口。

不追求爆款，不公开扩张，目标是让少量长尾插件形成自动流水收入。
